# 硬件 I2C 读写 MPU6050（10-2）· 总结

> 工程：`01-标准库学习/10-2硬件I2C读写MPU6050`
> 平台：STM32F103C8T6 + 标准库，I2C2（PB10=SCL，PB11=SDA）
> 时间：2026-10-28

---

## 一、一句话概括

10-1 的软件 I2C 是**人肉翻电平**：你自己拉 SCL/SDA、自己数时钟、自己看应答。
10-2 的硬件 I2C 是**把翻电平的活交给外设**：你只负责“下命令（写 DR）+ 等事件（查 SR）”，时序由硬件产生。

---

## 二、和 10-1 的对照

| | 软件 I2C（10-1） | 硬件 I2C（10-2） |
|---|---|---|
| 谁产生时序 | CPU 用 `delay_us` 一位一位翻 | I2C 外设硬件自动产生 |
| 引脚 | **任意**两个 GPIO | **固定** PB10/PB11（I2C2 默认引脚，需复用开漏） |
| 时钟 | APB2（GPIO） | APB1（I2C2，36MHz） |
| 速度 | 约 20kHz，由 delay 决定 | `I2C_ClockSpeed` 设定（50k/100k/400k） |
| CPU 占用 | 全程忙等 | 写 DR 后硬件自己发，CPU 只等事件 |
| 代码量 | 多：起始/停止/收发/应答全自己写 | 少：一个动作一个函数 |
| 可移植性 | 换芯片只改 GPIO | 换芯片要重写外设配置 |
| 调试难度 | 时序看得见，逻辑直白 | **事件顺序错一步就卡死** |

**选型经验**：引脚紧张、速率要求不高 → 软件 I2C 更省事；要 400kHz、要省 CPU、要多路 → 硬件 I2C。

---

## 三、核心：事件（Event）驱动

硬件 I2C 每一步做完会置一组状态位，SPL 把这些位拼成一个 32 位数，用 `I2C_CheckEvent()` 比对。**必须严格按顺序等**，跳一步后面就永远等不到。

| 事件宏 | 含义 | 什么时候出现 |
|---|---|---|
| `I2C_EVENT_MASTER_MODE_SELECT`（EV5） | 起始条件已发出，主模式 | `I2C_GenerateSTART` 之后 |
| `I2C_EVENT_MASTER_TRANSMITTER_MODE_SELECTED`（EV6） | 地址+**写**被从机应答 | 发完 0xD0 之后 |
| `I2C_EVENT_MASTER_RECEIVER_MODE_SELECTED`（EV6'） | 地址+**读**被从机应答 | 发完 0xD1 之后 |
| `I2C_EVENT_MASTER_BYTE_TRANSMITTING`（EV8） | 数据寄存器空，可以写下一字节 | 写 DR 之后 |
| `I2C_EVENT_MASTER_BYTE_TRANSMITTED`（EV8_2） | 最后一字节连移位寄存器都发完了 | 最后一个字节之后 |
| `I2C_EVENT_MASTER_BYTE_RECEIVED`（EV7） | 收到一字节，DR 里有数据 | 读方向接收时 |

**为什么区分 EV8 和 EV8_2**：EV8 只说明 DR 空了（还能装下一个），EV8_2 说明**连移位寄存器也空了**。
中间字节等 EV8（快），每段事务的**最后一字节必须等 EV8_2**（否则 STOP 会提前掐断最后一位）。

## 四、两条事务流程（照着代码走一遍）

### 写一个寄存器 `MPU6050_WriteReg`

```
START ──EV5──► 发 0xD0(写) ──EV6──► 发寄存器地址 ──EV8──► 发数据 ──EV8_2──► STOP
```

对应代码 8 行，每个 `WaitEvent` 都不能省。

### 读一个寄存器 `MPU6050_ReadReg`

```
START ──EV5──► 发 0xD0 ──EV6──► 发寄存器地址 ──EV8_2──►
   ↑ 重复起始（不清总线）
ReSTART ──EV5──► 发 0xD1(读) ──EV6'──► 关应答 + 置 STOP ──EV7──► 读 DR ──► 恢复应答
```

**这里最容易写错的是最后三个动作的顺序**：

```c
I2C_AcknowledgeConfig(I2C2, DISABLE);   // ① 先告诉从机"别再发了"
I2C_GenerateSTOP(I2C2, ENABLE);         // ② 立刻预约停止条件
while (I2C_CheckEvent(I2C2, I2C_EVENT_MASTER_BYTE_RECEIVED) != SUCCESS);  // ③ 等这一字节到
Data = I2C_ReceiveData(I2C2);           // ④ 读走
I2C_AcknowledgeConfig(I2C2, ENABLE);    // ⑤ 恢复，别影响下次
```

如果先读 DR 再关应答，从机会认为主机还要下一个字节，继续把数据推上总线，STOP 也会迟到。

## 五、这版代码的代价：12 次单字节读

`MPU6050_GetData` 里 6 个量、12 个字节，每个字节都调用一次 `MPU6050_ReadReg`，也就是 **12 趟完整事务**：

- 50kHz 下一趟约 0.6ms → 一帧接近 **7ms**，OLED 刷新肉眼可见地慢
- 而且 X/Y/Z 是**不同时刻**的样本，动起来数据会对不上

优化方向（和 10-1 的改法一样）：从 `0x3B` 开始**连续读 14 字节**，一趟事务拿到全部数据。
硬件 I2C 做连续读要用循环，并**倒数计数决定最后一个字节关应答**：

```c
for (i = 0; i < 14; i++)
{
    if (i == 13) { I2C_AcknowledgeConfig(I2C2, DISABLE); I2C_GenerateSTOP(I2C2, ENABLE); }
    while (I2C_CheckEvent(I2C2, I2C_EVENT_MASTER_BYTE_RECEIVED) != SUCCESS);
    Data[i] = I2C_ReceiveData(I2C2);
}
I2C_AcknowledgeConfig(I2C2, ENABLE);
```

## 六、这次修掉的两处笔误

| 位置 | 原来 | 问题 |
|---|---|---|
| `MPU6050_WaitEvent` | `while(...);` 后面多一个分号 | 超时逻辑变成独立代码块 → **死等**，传感器不应答就永久卡住 |
| `MPU6050_Init` | 开了 GPIOB 时钟，却 `GPIO_Init(GPIOA, ...)` | PB10/PB11 根本没配成复用开漏 → **总线完全不通**，ID 读不到、事件等不来 |

另外给 `MPU6050.h` 补了 `#include "stm32f10x.h"`，`MPU6050.c` 补了 `#include "MPU6050.h"`，让编译器能检查声明和实现一致。

## 七、硬件 I2C 的坑（比软件 I2C 多）

1. **事件顺序不能省**：少等一个 EV，下一个 EV 永远不来，程序看起来像死机。
2. **必须加超时**：F103 的硬件 I2C 有已知勘误，某些时序下 BUSY 位会卡住；生产代码要 `Timeout` + 出错后 `I2C_SoftwareResetCmd` 或重新 `I2C_Init`。
3. **上拉电阻**：PB10/PB11 是开漏，必须有上拉（MPU6050 模块板载 4.7k）。
4. **引脚别配错**：`GPIO_Init` 的端口和 `RCC_APB2PeriphClockCmd` 的端口必须是同一个（这次就在这翻了车）。
5. **地址格式**：`I2C_Send7bitAddress` 收的是**已经左移过的 8 位地址**（0xD0），函数内部自己处理最低位的读写方向。
6. **读最后一个字节**：NACK + STOP 必须提前置，顺序见第四节。
