## 0. 一句话总结

9-3 / 9-4 写出了**三状态接收状态机**，方向完全正确；但有几处「不改就收不到 / 收久了会崩」的硬伤：

1. **`NVIC_Init()` 被漏掉**（9-2、9-3、9-4 三个工程都有）→ 接收中断根本进不去；
2. **9-4 的字符串没有补 `'\0'`** → `strcmp` 会读越界；
3. **9-3 的 `pRxPacket` 收到第二包时才复位（实际上根本没复位）** → 写数组越界，踩坏相邻变量；
4. **头文件声明的函数名和实现名对不上**（`SendString` / `Serial_SendString`、`LED_Init` / `key_Init`）→ 隐式声明，换个编译器直接报错。

下面按「致命 → 逻辑 → 细节」分级列出，全部已在仓库代码中修正，并标了 `★`。

## 1. 致命问题（不改就收不到数据）

### 1.1 三个工程都漏了 `NVIC_Init()`

原代码（9-2 / 9-3 / 9-4 一模一样）：

```c
NVIC_InitTypeDef NVIC_InitStructure;
NVIC_InitStructure.NVIC_IRQChannel = USART1_IRQn;
NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;
NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 1;
NVIC_InitStructure.NVIC_IRQChannelSubPriority = 1;
/* ← 这里少了一行 NVIC_Init(&NVIC_InitStructure); */
```

**后果**：`USART_ITConfig()` 只是把 USART 的 RXNE 事件「挂到中断线上」，`NVIC_Init()` 才是去 NVIC 的 ISER 寄存器里**打开这个通道**。少了这一行：

- NVIC 里 USART1 通道是关的；
- 字节来了，SR 的 RXNE 置 1、中断挂起位也置 1，但 CPU 不会跳进 `USART1_IRQHandler`；
- 表现就是：**能发不能收**，`Serial_RxFlag` 永远是 0，OLED 第 4 行永远是空的。

这条配置是「外设 → NVIC → CPU」三级开关里的第三级，写串口接收时最容易漏：

| 级 | 打开的东西 | 代码 |
|---|---|---|
| 1 | 外设时钟 | `RCC_APB2PeriphClockCmd(RCC_APB2Periph_USART1, ENABLE)` |
| 2 | 外设的中断源 | `USART_ITConfig(USART1, USART_IT_RXNE, ENABLE)` |
| 3 | NVIC 通道 | `NVIC_Init(&NVIC_InitStructure)` ← **漏的就是这级** |
| 4 | 外设总开关 | `USART_Cmd(USART1, ENABLE)` |

### 1.2 9-4：字符串没有 `'\0'` 结尾

原代码收到 `'\r'` 时只切状态，**没有写结束符**：

```c
if (RxData == '\r') { RxState = 2; }   /* Serial_RxPacket 里没有 '\0' */
```

`Serial_RxPacket` 是全局变量（默认清零），所以短帧「碰巧」能用；但只要收到一帧把 100 字节缓冲区写满，后面就没有 `'\0'`，`strcmp()` 和 `OLED_ShowString()` 会一路读下去，读到栈/其他全局变量里，行为完全不可预测。

修正：

```c
if (RxData == '\r')
{
	Serial_RxPacket[pRxPacket] = '\0';   /* ★ 必须先封口再交给主循环 */
	RxState = 2;
}
```

**记住**：中断里收到的是「字节 + 长度」，主循环要的是「C 字符串」，中间那一步补 `'\0'` 必须自己做。

### 1.3 9-3：`pRxPacket` 不复位 → 数组越界

原代码状态 0 里只做了 `RxState = 1`，**没有把 `pRxPacket` 清零**：

```c
if (RxData == 0xFF) RxState = 1;        /* pRxPacket 还是上一包留下的 4 */
```

于是第二包数据直接写进 `Serial_RxPacket[4]`、`[5]`、`[6]`……而数组只有 4 字节。踩到的正好是紧挨着的 `Serial_RxFlag` / `RxState`，典型现象是：**第一包能显示，第二包开始花屏、卡死、或 flag 乱跳**。

修正（每个包头都要重置写指针）：

```c
if (RxData == SERIAL_PACKET_HEAD)
{
	pRxPacket = 0;     /* ★ 每包从 0 开始 */
	RxState = 1;
}
```

> 这类 bug 编译器不会报错，仿真时也很难一眼看出来——数组越界是嵌入式里最难查的一类问题。养成习惯：**任何「长度累加」的变量，都要问一句「谁负责清零」**。

### 1.4 9-4：头文件声明 `char[4]`，实现却是 `uint8_t[100]`

```c
/* Serial.h */
extern char Serial_RxPacket[4];        /* 大小 4，类型 char */
/* Serial.c */
uint8_t Serial_RxPacket[100];          /* 大小 100，类型 unsigned char */
```

同一个对象在两个编译单元里类型和大小都不一样，属于**未定义行为**。链接器不管类型只认符号地址，所以「能跑」，但：

- 别的文件里写 `sizeof(Serial_RxPacket)` 得到 4，不是 100；
- `strcmp(Serial_RxPacket, ...)` 传 `uint8_t*` 给 `char*` 形参 → 类型不兼容警告；
- 谁哪天在头文件里加个 `memcpy` 就会静默截断。

修正：统一用 `char` + 宏定义长度，头文件里写完整大小：

```c
#define SERIAL_RX_BUFFER_SIZE 100
extern char Serial_RxPacket[SERIAL_RX_BUFFER_SIZE];
```

### 1.5 头文件和实现「各说各话」

| 文件 | 头文件里声明的 | 实际实现的 | 后果 |
|---|---|---|---|
| 9-3 Serial.h | `SendString()` | 无 | 一调用就 `undefined symbol` |
| 9-3 Serial.h | `Serial_Printf()` | 无 | 同上 |
| 9-4 Serial.h | `SendString()` | `Serial_SendString()` | `main.c` 里调用 `Serial_SendString` 触发**隐式声明**警告 |
| 9-3 key.h | `LED_Init()` | `key_Init()` | `main.c` 调用 `key_Init()` 触发隐式声明 |

隐式声明在 Keil **AC5** 下只是警告（按 `int f()` 处理，恰好能跑）；换成 **AC6（armclang）/ C99** 就是 **error**，或者参数类型不是 `int` 时直接跑飞。

**规矩**：头文件 = 这个模块对外的合同。声明了就一定要有实现，实现了就一定要声明；ISR（`USART1_IRQHandler`）不该写进驱动头文件，它由启动文件里的向量表引用，不该有第二个声明。

## 2. 逻辑健壮性问题

### 2.1 9-3：状态 2 会「卡死」

收到包尾 `0xFE` 才回状态 0；如果因为丢字节、噪声，让状态机在状态 2 收到一个既不是包尾也不是包头的字节，原代码什么都不做 → **永远停在状态 2**，之后所有数据都被当包尾，再也收不到包。

修正：给状态机留「出错重来」的出口。

```c
case 2:
	if (RxData == SERIAL_PACKET_TAIL)      { Serial_RxFlag = 1; RxState = 0; }
	else if (RxData == SERIAL_PACKET_HEAD) { pRxPacket = 0;  RxState = 1; } /* 包尾丢了，当新包头 */
	else                                   { RxState = 0; }                  /* 整包作废，重找 */
	break;
```

这就是状态机和「写死的 if 链」的区别：**状态机必须能自恢复**，不能有一条路进去出不来。

### 2.2 9-4：缓冲区完全没有上限

原代码 `Serial_RxPacket[pRxPacket++] = RxData;` 没有任何越界检查。发 120 个字符（用串口助手按住 A 再回车），直接写穿 100 字节缓冲区。

修正：满了就丢弃多余字节，宁可截断也不能越界。

```c
else if (pRxPacket < SERIAL_RX_BUFFER_SIZE - 1)
{
	Serial_RxPacket[pRxPacket] = RxData;
	pRxPacket++;
}
/* 缓冲区满了：丢弃，但仍然等 '\r' 把这一帧走完，保证状态机能回到 0 */
```

### 2.3 9-4：`'@'` 分支缺大括号，缩进骗了眼睛

```c
if(RxData=='@'&&Serial_RxFlag==0)
	RxState=1;
	pRxPacket=0;        /* 缩进像是 if 里面，其实在 if 外面！ */
```

`pRxPacket = 0` 是**无条件执行**的：只要在状态 0，来任何一个字节都会清写指针。本例里状态 0 只等 `'@'`，问题不明显；但这种「单行 if 不带大括号」在嵌入式里迟早出事（后面加一行就变成新的坑）。**所有 if/for/while 一律带大括号**。

### 2.4 9-4：`Serial_RxFlag` 还是 1 时会丢新帧

状态 0 的进入条件是 `RxData=='@' && Serial_RxFlag==0`。如果主循环还没取走上一帧（flag 仍为 1），新来的帧会被**整帧丢弃**（`'@'` 被忽略，后面的正文全被当噪声）。

这是「一问一答」场景下的合理取舍（避免生产快于消费），但要知道这是**有意的丢帧**，不是 bug。更通用的做法是 **环形缓冲 + 读写指针**，让中断只管塞、主循环慢慢取。

### 2.5 9-4：重复清标志

```c
if (Serial_GetRxFlag() == 1) { ... }   /* 里面已经清零 */
Serial_RxFlag = 0;                     /* 又来一次，多余 */
```

`Serial_GetRxFlag()` 的设计就是「读到 1 就清 0」，外面再清一次属于二次操作。如果这段代码哪天挪到 `if` 外面，还会把「刚收完、还没来得及处理」的下一帧标志抹掉。删掉。

### 2.6 9-3 里的「死代码」和魔法数字

- 注释掉的 `Serial_SendString / Serial_Pow / Serial_SendNumber / fputc / Serial_Printf` 是 9-1、9-2 的遗留。9-3 用不到就整段删掉，**注释掉的代码不是文档，是噪声**（要留就留成笔记，不要留在工程里）。
- `0xFF` / `0xFE` / `4` 到处裸写。改成 `SERIAL_PACKET_HEAD` / `SERIAL_PACKET_TAIL` / `SERIAL_PACKET_SIZE`，改协议时只改一处。
- 两个全局数组的注释**写反了**：`Serial_TxPacket` 注释成「接收字节」、`Serial_RxPacket` 注释成「接收标志位」。
- 工程根目录还有个 0 字节的 `LED.c`，Keil 工程文件里根本没引用它——多余文件，已不上传。

### 2.7 9-4 main 里的三处小错

| 位置 | 原代码 | 问题 |
|---|---|---|
| LED_OFF 分支 | `Serial_SendString("LED_ON_OFF\r\n")` | 串口回 `LED_ON_OFF`，OLED 显示 `LED_OFF_OK`，两边不一致（应为 `LED_OFF_OK`） |
| else 分支 | OLED 显示 `"ARROR_COMMAND"` | `ERROR` 拼成 `ARROR`，串口发的是对的 |
| 第 1 行 | `OLED_ShowString(1,1,"TxPacket")` | 本课根本没有「发送数据包」，是从 9-3 抄过来的残留标签 |

另外 `OLED_ShowString(4,1,Serial_RxPacket)` 直接把整行丢给 OLED：**超过 16 个字符会算出 128 以外的地址，显示错位/花屏**。已加 `ShowRxText()`，只取前 16 字符并用空格补齐（补空格同时解决「上一帧更长、这一帧更短时残留字符」的问题）。

### 2.8 中断和主循环共享的变量要 `volatile`

```c
volatile uint8_t Serial_RxFlag;    /* ISR 里写，main 里读 */
```

不开优化时加不加都能跑；一旦开 `-O2`，编译器可能把 `if (Serial_RxFlag == 1)` 的读操作提到循环外面缓存起来，于是**永远读到 0**。凡是「中断改、主循环读」的变量，一律加 `volatile`。同理，`Serial_RxPacket` 这种「中断写、主循环读」的数组，要么用 `volatile`，要么在取数据时关一下中断（临界区）。

### 2.9 关于 `Serial_SendByte` 的「先写后等」——顺带纠正笔记里的一句话

`04-笔记/2026-10-22-串口USART全章总结.md` 里写：

> 反过来（先等再写）第一个字节就卡死——TDR 本来就空，TXE 一直 SET，会先空等一轮。

**这句话不准确**。TDR 空时 TXE = 1，`while(TXE == RESET);` 的条件一开始就是假，**立即通过，不会卡死**。两种写法都对：

| 写法 | 行为 | 差别 |
|---|---|---|
| 写 → 等 TXE | 写完等 TDR 腾空；最后一字节仍在移位寄存器里 | 江协/本仓库统一用这种，函数返回时 TDR 一定空 |
| 等 TXE → 写 | 先确认能写再写；函数返回时数据可能还在 TDR | 少一次「空等」，效率略高 |
| 末尾再等 **TC** | 等最后一字节真正移出引脚 | 关串口 / 进低功耗 / 切 RS485 方向前**必须**等 TC |

结论：现有写法没问题，不用改；但要记住 **TXE 只管「TDR 空」，TC 才是「移位寄存器也空了」**。

### 2.10 顺手修的 9-2：`sprintf` 传 `va_list` 是错的

9-2 的 `Serial_Printf` 用了：

```c
va_start(arg, format);
sprintf(String, format, arg);    /* ❌ 把 va_list 当成"一个参数"传进去 */
```

`va_list` 不是普通变量，不能这么传，应该用专为可变参数设计的 `vsprintf`：

```c
vsprintf(String, format, arg);   /* ✅ 9-2 已改 */
```

否则 `Serial_Printf("Num=%d", 123)` 打印出来的是栈上的垃圾值。

## 3. 知识点整理

### 3.1 为什么需要「数据包」？

串口是**字节流**：`USART_ReceiveData()` 一次只给你 1 个字节，硬件不告诉你「这一帧从哪开始、到哪结束」。所以：

- **单字节收发**（9-1/9-2）→ 一个字节就是全部信息，简单；
- **多字节信息**（一串坐标、一条指令）→ 必须自己定协议，否则主循环无法判断「数据收齐了没有」。

定界（frame delimiting）就是把字节流重新切回「消息」的过程，**只有三种基本套路**：

| 方案 | 格式 | 优点 | 缺点 | 本仓库 |
|---|---|---|---|---|
| 包头 + 包尾 | `0xFF [D0..D3] 0xFE` | 实现最简单、自同步 | 数据里出现包头/包尾会歧义（靠状态机规避） | 9-3 |
| 包头 + 长度 + 校验 | `0xAA [Len] [Data...] [CRC]` | 最通用、可传任意二进制 | 要多写长度/校验 | 后续（Modbus 就是这种） |
| 分隔符（文本） | `@LED_ON\r\n` | 人可读、串口助手直接敲 | 效率低、要处理转义、依赖字符串结尾 | 9-4 |

### 3.2 9-3：HEX 定长包的三状态机

协议：`0xFF` + 4 字节 + `0xFE`，共 6 字节。

```text
         收到 0xFF                收满 4 字节              收到 0xFE
  ┌──────┐ ────────► ┌──────┐ ──────────────► ┌──────┐ ────────► 置 flag，回状态 0
  │ 0 找 │           │ 1 收 │                 │ 2 等 │
  │ 包头 │ ◄──────── │ 数据 │                 │ 包尾 │
  └──────┘   出错/超时 └──────┘ ◄──────────── └──────┘
```

**为什么用状态机而不是「收满 6 个字节再判断」**：状态机**边收边判断**，不需要 6 字节的中间缓冲，RAM 只要 4 字节；而且能在任意时刻被打断（中断本来就是被反复打断的），`static` 变量天然把状态留在两次中断之间。

**`static` 局部变量为什么必须**：

```c
void USART1_IRQHandler(void)
{
	static uint8_t RxState = 0;      /* 放在静态区，函数返回也不丢 */
	static uint8_t pRxPacket = 0;
}
```

普通局部变量在栈上，ISR 一返回就没了 → 每次都从状态 0 开始 → 永远收不完一包。

### 3.3 9-4：文本包的三状态机

协议：`'@'` + 正文 + `'\r\n'`。

```text
 状态 0：等 '@'（并且上一帧已被取走）→ 清写指针，进状态 1
 状态 1：普通字符 → 存进 buffer、指针 +1
         '\r'    → buffer[指针] = '\0'，进状态 2
         满了    → 丢弃多余字节（仍然等 '\r'）
 状态 2：'\n'    → 置 flag，回状态 0（'\r\n' 只认最后那个 '\n' 才算收完）
```

**为什么 `'\r'` 和 `'\n'` 要分两个状态**：串口助手「发送新行」默认发 `\r\n` 两个字节。如果见到 `'\r'` 就置 flag，主循环可能在 `'\n'` 还没到时就取走数据——大部分时候没事，但紧接着的 `'\n'` 会被当成下一帧的噪声。用「`\r` 收尾 + `\n` 确认」最稳，也顺便把 CR/LF 丢在缓冲区外。

### 3.4 HEX 包 vs 文本包

| | HEX 包（9-3） | 文本包（9-4） |
|---|---|---|
| 传输内容 | 任意二进制 | 可见 ASCII |
| 调试 | 串口助手要开 HEX 模式 | 直接敲 `@LED_ON` |
| 定界 | 包头/包尾 | `@` + `\r\n` |
| 长度 | 固定（4 字节） | 不定长（本例 ≤99） |
| 解析 | 无需解析，直接是数据 | 需要 `strcmp` 比较命令 |
| 典型场景 | 传感器数据、无线模块 | 命令行、AT 指令、上位机调试 |

### 3.5 中断服务函数的两条铁律

1. **快进快出**：ISR 里只做「搬字节 + 改状态 + 置标志」，不做 `strcmp`、不做 `OLED_ShowString`、不做 `delay`。
   - `strcmp` 挪到主循环：9-4 就是这么做的（ISR 只收，main 里判断）。
   - OLED 走的是软件 I2C，一次刷新几百微秒，放中断里会拖慢一切。
2. **不阻塞、不重入**：ISR 里不要 `while` 等硬件（除极短的 TXE 等待）、不要调会阻塞的函数。

配套的「主循环模式」：

```c
while (1)
{
	if (Serial_GetRxFlag() == 1)     /* ① 有没有新数据？ */
	{
		/* ② 处理：解析命令、执行动作 */
		/* ③ 回应/显示 */
	}
	/* ④ 其他任务 */
}
```

这就是最朴素的「**中断置标志 + 主循环轮询处理**」，后面学 RTOS 时，信号量/消息队列本质上就是把「标志 + 缓冲区」做成了系统对象。

### 3.6 `strcmp` 与字符串的坑

- `strcmp(a, b) == 0` 表示**相等**（返回 0 是「没差别」），不是「成功」；
- 比较的是 `'\0'` 之前的内容 → 缓冲区必须有 `'\0'`（1.2 的 bug 就出在这）；
- 大小写敏感：`"led_on"` ≠ `"LED_ON"`；要忽略大小写用 `strcasecmp`（非标准，自己写一个循环更稳）；
- 命令带尾随空格（`"LED_ON "`）也会比较失败 → 实际项目里先 `trim` 再比较；
- 别把 `if (strcmp(...))` 当「相等」用——那是「不相等」。

### 3.7 排错清单（按症状查）

| 症状 | 大概率原因 |
|---|---|
| 能发不能收，第 4 行永远空 | 漏 `NVIC_Init()`（1.1）；或忘了 `USART_ITConfig` |
| 收到的第一包对，后面全乱 / 死机 | 数组越界（1.3）、没补 `'\0'`（1.2） |
| 串口助手显示乱码 | 波特率不一致；`printf` 重定向没勾 MicroLIB；编码不是 UTF-8 |
| 只收到第一个字符 | ISR 里没读 DR（RXNE 不清，反复进中断）或主循环清标志太快 |
| OLED 上一条命令的残留还在 | 显示前没清行（本仓库用补空格解决） |
| 单步调试正常，全速运行就错 | 共享变量没加 `volatile`（2.8） |
| 长字符串显示错位/花屏 | 超过 16 字符还往一行里塞（2.7） |
| 收一帧后就不再响应 | 状态机没有出错出口（2.1） |

## 4. 「三改」练习（学完这两节该动手的）

1. **改包头包尾**：把 9-3 的协议改成 `0xA5 ... 0x5A`，并在数据里故意塞 `0xFF 0xFE`，验证状态机不会误触发。
2. **加长度字节**：9-3 改成 `0xAA [Len] [Len 字节数据] [校验和]`，验证 1~10 字节不定长包。
3. **加校验**：给 9-3 包尾前加一个「前 4 字节之和的低 8 位」，错一字节就整包丢弃。
4. **环形缓冲**：把 9-4 的单缓冲换成 128 字节环形队列（读/写指针），解决快发丢帧（2.4）。
5. **多命令**：9-4 加 `LED_TURN` / `BEEP_ON` / `GET`（回读当前 LED 状态），练「命令表」而不是 `if-else` 链。
6. **上位机**：用 Python `pyserial` 写个脚本，按键发 `@LED_ON\r\n`，收到回复就打印——把「协议」这件事从单片机扩到 PC 端。
